# 架构

[← 文档首页](README.md)

监控插件有一个高于一切的义务：**它绝不可以是拖慢服务器的元凶。** 此处的每个设计决策都遵循这一原则，本页主要是记录权衡在哪里做出以及为什么这样选择。

## 层级结构

```
                    ┌──────────────────────────────────────────┐
   主线程            │  TickSampler   1/tick    <0.01 ms        │
                    │  MetricsService  1/s     TPS、堆内存、CPU │
                    │  WorldStats      1/5s    O(实体)         │
                    │  MapService      1/tick  N 个快照         │
                    │  EventCapture    事件触发时               │
                    └───────────────┬──────────────────────────┘
                                    │ 通过 volatile 交换的快照
                    ┌───────────────▼──────────────────────────┐
   独立线程          │  SpikeWatchdog   栈捕获                   │
                    │  StorageWriter   批量 SQLite 写入          │
                    │  EventStream     一个写入者，所有客户端     │
                    │  AlertDispatcher HTTP 推送                │
                    │  MapRenderer     PNG 编码                 │
                    └───────────────┬──────────────────────────┘
                                    │
                    ┌───────────────▼──────────────────────────┐
   HTTP 工作线程     │  WebServer  →  路由  →  处理器            │
                    │  读取：来自缓存，绝不直接访问 Bukkit        │
                    │  写入：跳转到主线程，带超时                  │
                    └──────────────────────────────────────────┘
```

箭头编码的规则：**主线程生产，其他所有线程消费。** 没有 HTTP 请求需要为读取而等待 tick 循环。

## 卡顿归因

这是其余设计所要支持的核心功能。

知道一个 tick 耗时 800 ms 几乎毫无用处。知道在那 800 ms 期间**服务器在做什么**才是关键——而当 tick 结束时，证据已经消失。

因此有两个组件：

**采样器**作为一个 1-tick 重复任务运行。每次调用与上一次调用之间恰好间隔一个完整的 tick 工作，因此它们之间的间隔就是 tick 的真实持续时间：健康服务器上为 50 ms，服务器落后时则为实际的耗时。开销仅为一次 `nanoTime`、一次数组存储、一次比较。

**看门狗**是一个单独的守护线程，监视采样器发布的时间戳。一旦 tick 运行时间超过阈值，它就在 tick **仍然卡住时**获取主线程的栈跟踪，将其解析到某个插件，并将结果交回。采样器在 tick 最终结束时将该证据与精确的持续时间合并。

两个真实的成本。`Thread.getStackTrace()` 在另一个线程上需要该线程到达一个安全点，因此卡在紧凑计数循环中的 tick 可能会延迟捕获直到循环结束——看门狗阻塞，而非服务器。而且捕获并非免费，这就是它有速率限制的原因。

### 为什么使用 tick 周期而非 MSPT

它们是不同的数字，GodView 会从各自的正确来源报告两者。

- **MSPT** 是 Paper 的测量值：花在工作上的时间，排除空闲 tick 末尾的休眠。在空闲服务器上读数约为 2 ms。
- **Tick 周期**是两个 1-tick 任务之间的间隔：`max(50 ms, 实际工作时间)`。在空闲服务器上读数为 50 ms。

周期对于延迟检测至关重要——300 ms 的周期意味着 250 ms 的超时，无论原因是什么。将周期报告为 MSPT 会偏差一个数量级。

### 责任判定

归因从最内层帧向外遍历捕获的栈，并命名它遇到的第一个插件，匹配基于每个已加载插件的主类构建的包前缀。

最内层优先使其正确而非仅仅合理：当插件调用服务端且时间是消耗在服务端时，插件帧仍然位于下方并获得责任归属——这是诚实的，因为插件选择了发起该调用。

前缀包含祖先包，因此主类位于 `com.example.core` 的插件在 `com.example.listeners` 中也能被识别。被两个不同插件声明的祖先包会被双方丢弃而非猜测，匹配优先选择最长的前缀。

来自另一个线程的 `StackTraceElement` 只携带名称，因此将每个解析为 `Class` 意味着在看门狗线程上进行类加载——开销大，且可能作为诊断的副作用运行静态初始化器。包前缀是正确的权衡。

## 自动降级

`performance.profile: auto` 根据 TPS 变化在三个档位之间切换。档位**缩放**配置的数值而非替换它们，因此任何自行调整过数值的人都会保留他们的比例。

**10 秒**连续不良表现后降级；**60 秒**良好表现后恢复。结合两个阈值之间的间隔，在数值和时间上都提供了迟滞——徘徊在边界上的服务器会稳定在一个档位上而非来回抖动。

`low` 档**不会**禁用的功能：tick 采样和栈捕获。服务器吃力的时候恰恰是你需要知道哪个插件在占用 tick 的时候，因此捕获频率减半而非完全关闭。

## 空闲挂起

没有人在观看时，开销较大的采集工作完全停止。低成本的采样继续运行，因为告警规则依赖它，且其开销几乎为零。

订阅者计数来自实时流，而断开的客户端只能通过写入来发现——这就是 TCP 能报告的全部，而且通常不是第一次尝试，因为写入对端已关闭的 socket 通常会先进入本地缓冲区，在第二次写入时才会失败。有帧流动时，这在几秒内就能解决；在完全空闲的流上，心跳将其限制在约二十秒。因此计数在有人关闭标签页后可能会短暂偏高。替代方案是活跃度探测，其开销比它要避免的采集工作还要高。

## 存储

一条规则：主线程从不等待磁盘。

每次写入进入一个有界队列，由单个线程排空并批量处理为一个事务。当队列填满时——磁盘卡顿、事件爆发——数据行被**丢弃并计数**而非对 tick 产生背压。丢失一条审计记录很糟糕，但拖慢服务器以写入一条记录更糟糕，而且计数可见，因此取舍从不默默发生。

单写入者还消除了写锁定的需要，因为 SQLite 无论如何都会序列化写入者。读取者使用单独的连接，WAL 日志模式使其可以在不阻塞写入者的情况下运行。`purge()` 将请求入队而非内联执行，因为 JDBC 连接不是线程安全的，而从主线程进行保留期清理会在底层使用写入者的连接。

图表查询在 SQL 中分桶。一个月的采样是二十五万行，没有任何一行需要加载到堆内存中求平均。桶宽来自样本实际覆盖的时间跨度，而非请求的跨度——开放式范围否则会将所有内容折叠为一个点。

## Web 层

使用 JDK 自带的 `com.sun.net.httpserver`。没有阴影框架、没有额外的兆字节、没有与 Minecraft 服务器已有的 Netty 产生类加载器冲突。

**授权存在于路由表中**，而非处理器体内。路由在注册时带有所需的权限，因此处理器中不会忘记检查；只有四个公共路由存在，它们在一个地方声明。

工作线程池故意保持很小，并且因为流式响应不会占用工作线程而保持可用：SSE 处理器写入头部，将流交给广播器然后返回。

### 值得命名的安全决策

- **`X-Forwarded-For` 是客户端写入的请求头。** 仅在 `behind-proxy` 开启*且*对端是受信代理时才查阅，然后取最右边的不受信跳，绝不取最左边——发送自己请求头的客户端，代理会将请求头附加到其后。
- **登录在检查密码之前先进行频率限制。** PBKDF2 花费我们的十分之一秒与花费攻击者的相同，因此无节制的端点会成为针对被监控服务器的拒绝服务攻击。
- **登录失败无法区分**，未知账号仍然对虚拟密码支付完整的哈希成本——提前返回会使"无此用户"在时间上可测量，从而枚举账号。
- **没有默认账号。** 在已知端口上附带 `admin/admin` 的面板会在数小时内被扫描器发现。
- **实时快照不携带 IP 地址。** 一个 SSE 帧发送给所有订阅者，无论其角色如何，因此角色相关的内容不能存在于其中。

## 面板

一个由 Maven 编译到 jar 中的 Vue 应用程序，在仅允许同源资源的 CSP 下提供服务。Vite 配置为不内联任何内容——将引导脚本内联的打包工具会生成在 `npm run dev` 下完美运行且仅在生产环境中失败的空页面，这就是测试套件通过真实的静态处理器服务构建输出并断言 CSP 针对生成的 HTML 的原因。

## 版本兼容性

一个 jar 包覆盖 1.21 到 1.21.11，针对其中最早的版本编译。在该范围内所有变化的内容通过反射在一个文件 `Compat` 中访问，在静态初始化器中解析一次，每个调用不再重复——每秒运行二十次的指标采样器无法承担 `getMethod` 查找的开销，更无法承担异常。

实际变化的内容：`Attribute` 枚举在 1.21.3 中变为注册表接口且 `GENERIC_MAX_HEALTH` 被重命名；`BanList.Type` 让位于顶层的 `BanListType`；Paper 更便宜的区块和方块实体计数器并非在每个分支上都存在。

## 测试

十一个套件，由 `mvn test` 运行，驱动真实组件而非模拟：绑定的 socket、磁盘上的 SQLite 文件、附加的 Log4j appender、从渲染器中解码回来的真实 PNG。比单元测试慢，但物有所值——它们捕获的大部分问题存在于组件之间的接缝处，而这正是模拟所掩盖的。

以下是一些捕获到的问题举例：

- SQLite 按*请求的*窗口而非数据自身的范围对图表数据分桶，因此开放式范围将 30 个采样折叠为一个点。内存后端没有这个 bug，这正是共享契约测试发现它的原因。
- SSE 流标记存在于 `ThreadLocal` 中，因此在流中间抛出的处理器会使其保持设置状态并泄漏连接。
- `log4j-core` 被锁定在 API 不匹配的版本上——普通编译不可见，在触及 `Configurator` 时致命。
